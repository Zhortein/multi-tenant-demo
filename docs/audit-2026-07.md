# Demo Application Technical Audit — July 2026

## Executive summary

The demo exposes a broad set of journeys—tenants, products, documents, notifications, email, and Messenger—but it is not yet an automated validation application for the bundle. It contains no application test cases, its CI disables migrations, Doctrine validation, and PHPUnit, its documentation uses obsolete configuration, and no effective access rules protect the advertised screens.

Health status: **red-amber as a regression reference** and **amber as a demonstration prototype**.

## Implemented functionality

- Tenant, Product, User, Document, and Notification entities; two migrations.
- Active path resolution with the shared-database strategy.
- Tenant/product CRUD, dashboards, and tenant navigation.
- Application services for local storage, email, and Messenger notifications.
- Docker Compose, FrankenPHP, PostgreSQL, Mailpit, and sample-data commands.

## Insufficiently demonstrated functionality

The `tests/` directory contains only the bootstrap. Project documents describe manual checks and demonstration buttons rather than reproducible assertions.

No test creates tenant A/B data and attempts cross-tenant reads, writes, direct identifier access, uploads, or messages. Mailer, Messenger, and storage are primarily demo-specific services and do not prove the public bundle contracts as an external consumer.

## Compatibility and reproducibility findings

- `php >=8.2` conflicts with the bundle requirement of `>=8.3`.
- Symfony is pinned to 7.3 while the local bundle proposal targets 7.4/8.0.
- Doctrine DBAL is `^3` and ORM `^3.5`; there is no DBAL 4 matrix.
- The bundle requirement is `dev-develop`, with no stable tag or explicit resolved-commit validation strategy.
- The README uses `resolution.strategy: path`; both the active configuration and bundle expect `resolver: 'path'`.
- The Makefile `install` target recreates and copies a skeleton into the repository, while `clean` removes volumes and runs `docker system prune`.
- PHPStan and CS Fixer targets are documented without corresponding development dependencies.
- The fixtures target expects DoctrineFixturesBundle, which is not declared.
- The README advertises users, administration, and authentication, but `security.yaml` comments out access controls and no login controller is apparent.
- Composer declares `proprietary` while the repository license and README state MIT.

## Security risks

Tenant management and email/storage/Messenger test routes appear to lack an effective authorization policy. Implementing `UserInterface` is not equivalent to providing authentication. Downloads and identifier-based lookups must check the current tenant independently of URL structure. Administrative operations must be separated from tenant routes and protected by explicit roles.

## CI and checks

- `docker compose config --quiet`: passed.
- Remote CI inspection: image build, startup, and HTTP/Mercure smoke checks are active; migrations, schema validation, and PHPUnit are guarded by `if: false`.
- Full installation/build was not run before establishing a safe dependency strategy; no local `vendor/` directory exists.
- PHPUnit, PHPStan, and style checks are not currently meaningful in the restored state; PHPUnit has no application test case to execute.

These are project and reproducibility limitations, not proof that every demonstration journey fails at runtime.

## Gaps relative to the bundle

The demo does not automatically exercise alternative resolvers, RLS, multi-database mode, the test kit, tenant-aware caching, or observability. It reimplements tenant-aware services without clearly exposing the boundary with bundle services. It should become the consumer test for every stable public API and test either a selected commit during development or a stable tag.

## Recommendations and effort

Align PHP, Symfony, Doctrine, and resolver configuration first. Make dependency installation immutable, then enable migrations, schema checks, and PHPUnit in CI. Add a focused end-to-end suite prioritizing cross-tenant denials and authorization boundaries.

Qualitative effort: **large, approximately 4–7 person-weeks**, depending on prior stabilization of the bundle API.
